# Техническое решение

## 1. Почему Vite подходит для MVP

Vite даёт быстрый запуск проекта, удобную разработку и компактную конфигурацию. Для публичной витрины и отдельной админ-панели оптимальной стартовой связкой будет React + TypeScript.

Важно: Vite — это инструмент сборки, а не backend или готовая платформа интернет-магазина. API, базу данных, файловое хранилище, аутентификацию, SEO-стратегию и оформление заказов необходимо реализовать или подключить отдельно.

## 2. Рекомендуемый стартовый стек

| Область | Решение | Причина |
|---|---|---|
| Сборка | Vite | быстрый и простой старт MVP |
| UI | React + TypeScript | единая компонентная модель для сайта и админки |
| Маршрутизация | React Router | понятная маршрутизация страниц каталога |
| Стили | CSS Modules + CSS variables | изоляция стилей без тяжёлого UI-фреймворка |
| Состояние сервера | TanStack Query | кэширование, мутации и состояния API |
| Формы | React Hook Form + Zod — при сложных формах | валидация и типизация |
| Unit/component tests | Vitest + Testing Library | совместимость с Vite |
| E2E | Playwright | проверка основных пользовательских сценариев |

Backend-фреймворк, СУБД и хранилище файлов будут выбраны отдельным архитектурным решением. Предварительно нужна реляционная база данных, поскольку товары, варианты, роли, остатки и заказы имеют связанные и транзакционные данные. Зависимости добавляются только тогда, когда для них появляется конкретная задача.

## 3. Компоненты системы

```text
Публичный сайт ─┐
                ├── Backend API ── База данных
Админ-панель ───┘        │
                         ├── Файловое хранилище
                         └── Почта / уведомления / платежи
```

- **Публичный сайт** читает только опубликованные данные и отправляет разрешённые публичные формы.
- **Админ-панель** работает с закрытыми методами API и никогда не считается доверенной стороной сама по себе.
- **Backend API** проверяет аутентификацию, права, входные данные и бизнес-правила.
- **База данных** хранит каталог, пользователей, роли, публикации, остатки и аудит.
- **Файловое хранилище** хранит оригиналы и подготовленные изображения; база хранит их метаданные и связи.

Для MVP разумно держать компоненты в одном репозитории, но развёртывать публичный сайт, админку и API независимо.

## 4. Предварительная структура репозитория

```text
apps/
  storefront/   # публичный сайт на Vite
  admin/        # закрытая админ-панель на Vite
  api/          # backend API
packages/
  contracts/    # общие схемы и типы API
  ui/           # только действительно общие UI-примитивы
  config/       # общая конфигурация инструментов
```

Структура будет уточняться по мере появления кода. Не следует заранее создавать пустые слои.

## 5. Маршруты MVP

```text
/                 Главная
/catalog          Каталог
/catalog/:slug    Страница товара
/about            О бренде
/delivery         Доставка и оплата
/contacts         Контакты
/*                404
```

Админ-панель рекомендуется разместить отдельным приложением, например на `admin.example.com`, а не смешивать её маршруты с публичным интерфейсом. Предварительные маршруты:

```text
/login
/dashboard
/products
/products/new
/products/:id
/categories
/content
/users
/audit
```

Фильтры каталога желательно отражать в URL, например:

```text
/catalog?type=miniature&available=true&sort=popular
```

Это позволит сохранять ссылку на выборку и корректно работать с историей браузера.

## 6. Модель товара

Предварительный контракт, не привязанный к конкретному API:

```ts
type Product = {
  id: string;
  slug: string;
  name: string;
  shortDescription: string;
  description: string;
  price: number | null;
  currency: "RUB";
  categoryId: string;
  tags: string[];
  images: ProductImage[];
  material?: string;
  dimensions?: string;
  finish?: "unpainted" | "painted" | "custom";
  availability: "in_stock" | "made_to_order" | "preorder" | "unavailable";
  leadTime?: string;
  featured: boolean;
};

type ProductImage = {
  src: string;
  alt: string;
  width: number;
  height: number;
};
```

Деньги в вычислениях следует хранить в минимальных единицах валюты либо использовать безопасный специализированный формат. Тип выше пока описывает только публичный интерфейс данных.

## 7. Управление данными

Локальные типизированные данные допустимы только для раннего визуального прототипа. Рабочий MVP получает данные через API и позволяет изменять их через админ-панель.

До реализации необходимо выбрать один из двух основных путей:

1. self-hosted headless CMS с расширениями для доменной логики;
2. собственный backend и собственная админ-панель.

Готовая CMS ускорит стандартные CRUD-операции, но нестандартные остатки, производство под заказ, варианты изделий и заказы могут потребовать собственного API. Решение принимается после описания этих правил, а не только по скорости разработки.

## 8. Аутентификация и роли

Минимальная ролевая модель:

| Роль | Возможности |
|---|---|
| Owner | полный доступ, управление администраторами и настройками |
| Editor | товары, категории, изображения и контент без управления доступом |
| Order manager | заявки, заказы, статусы и необходимые данные покупателей |

Если на старте системой пользуется только владелец, модель всё равно не должна предполагать единственного «вечного» пользователя.

Требования:

- пароли хэшируются современным алгоритмом и никогда не возвращаются API;
- сессии передаются через защищённые `HttpOnly` cookies либо эквивалентный безопасный механизм;
- закрытые операции проверяют разрешения на сервере;
- вход ограничивается по частоте попыток;
- восстановление доступа использует одноразовый ограниченный по времени токен;
- смена роли, удаление пользователя и другие критические действия журналируются;
- владелец не должен случайно удалить или лишить прав последнюю учётную запись Owner;
- персональные данные покупателей не смешиваются с публичным профилем товара и выдаются только нужным ролям.

MFA для роли Owner рекомендуется предусмотреть в архитектуре и оценить для первой версии.

## 9. Контракт API

Предварительные группы методов:

```text
/api/public/products
/api/public/categories
/api/public/content
/api/auth/*
/api/admin/products/*
/api/admin/categories/*
/api/admin/media/*
/api/admin/content/*
/api/admin/users/*
/api/admin/audit
```

Публичный и административный контракты разделяются. Черновики, внутренние заметки, персональные данные и служебные поля никогда не должны попадать в публичный ответ только потому, что присутствуют в одной таблице.

API должно иметь версионируемую документацию OpenAPI, единый формат ошибок, пагинацию, фильтрацию и серверную валидацию. Общие TypeScript-типы желательно генерировать из контракта или общей схемы, а не дублировать вручную.

## 10. SEO и рендеринг

Чистый клиентский Vite подходит для проверки интерфейса, но для публичного магазина органический поиск может быть важен. После подтверждения требований нужно выбрать:

- статическую генерацию страниц товаров;
- серверный рендеринг;
- либо статический клиентский MVP с последующей миграцией.

На первом этапе данные и UI следует отделить так, чтобы возможная миграция на SSR-фреймворк не потребовала переписывать доменную модель и компоненты.

## 11. Изображения и производительность

- хранить оригиналы отдельно от оптимизированных вариантов;
- использовать AVIF/WebP с резервным форматом при необходимости;
- задавать width и height для предотвращения скачков вёрстки;
- загружать изображения ниже первого экрана лениво;
- не использовать hero-изображение как неоптимизированный CSS-фон;
- проверять страницу на медленном мобильном соединении.

## 12. Безопасность и приватность

- не хранить секреты в клиентском коде;
- валидировать данные формы на клиенте и сервере;
- собирать только необходимые персональные данные;
- подключать аналитику и cookies только после согласования политики;
- оплату передавать сертифицированному платёжному провайдеру, не обрабатывая карточные данные самостоятельно.
- хранить секреты и ключи только на сервере;
- настроить резервное копирование базы и проверять восстановление;
- ограничивать тип, размер и количество загружаемых файлов;
- удалять метаданные изображений, если они могут раскрывать приватную информацию;
- защищать изменяющие запросы от CSRF при cookie-аутентификации;
- не разрешать CORS для произвольных источников.

## 13. Definition of Done для задачи

- реализованы согласованные состояния интерфейса;
- типы не обходятся через `any` без объяснения;
- компонент проверен на мобильной и десктопной ширине;
- интерактивные элементы доступны с клавиатуры;
- добавлены тесты для логики, где ошибка влияет на пользовательский сценарий;
- линтер, типизация и тесты проходят;
- документация обновлена, если изменились требования или архитектурное решение.
- административный сценарий проверен не только с ролью Owner, но и с ограниченной ролью;
- API не раскрывает закрытые поля в публичных ответах;
- миграции базы данных и способ отката описаны;
- для критических данных настроено и проверено резервное копирование.
